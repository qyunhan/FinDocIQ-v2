### A.1 The mapping layer is not in the pipeline

`run_doc.py` never invokes `mapping/*`. Steps 0–7 above are the pipeline;
`registry.py`, `backfill_map.py`, `apply_dashboard_rows.py`, `audit_coverage.py`
are run by hand. Consequence in §D.5.

### A.2 Fail-open gates beyond D9 / D11 / D14

## Part C — feature provenance

### C.1 `period`

**Decided in one place:** `pass2/load_v7.py:_load_table`, lines **1373-1385**.

```
col_period > eff_row_period > table_period > doc_period
```

Confirmed exactly as documented. The span is carried **paired** with whichever
axis won (`:1375,1381,1383,1385`) — a genuinely good property.

But the chain has a hidden fifth link. `table_period` is not independent:

```python
# load_v7.py:1100-1105
if all_cols_have_period:      table_period = table_span = table_start = None
elif title_ps:                table_period, table_span, table_start = title_ps
else:                         table_period, table_span, table_start = doc_period, None, None
```

So the real chain is
`col_period > row_period > table_title_period > **doc_period** > doc_period`,
and `doc_period` occupies **two** links. Census over all 24,788 cells:

| source | cells | share |
|---|---|---|
| `col_period` | 13,339 | 53.8% |
| `row_period` | 404 | 1.6% |
| `table_t.period` | 11,045 | **44.6%** |
| `doc_period` (direct) | 0 | 0% |

The direct `doc_period` link never fires because `table_period` already absorbed
it at `:1105`. **44.6% of cells inherit a period nobody printed on them.**

**Fallback chain empty:** `period is None` raises (`:1386-1389`) — genuinely
fail-loud. In practice unreachable: `run_doc.infer_period` (`:75`) exits if the
filename carries no period token, so `doc_period` is never NULL.

**Can a later stage overwrite it?** No. `cell_fact.period` is written once at
load and read verbatim by `v_cell`, `v_cell_flat` and `build_fact_metric`. The
period is **not** overwritten downstream — it is decided wrongly at the load and
faithfully propagated. That is the good news in this section.

**Empty = error or silent default?** Silent default, twice over (gates A1, A2,
A3).

**On the stated `col_lvl1='value'` hypothesis — the code does the opposite.**
`col_lineage` (`load_v7.py:809-828`) returns `["value"]` when *both* the group
banner and the leaf are period text, i.e. `'value'` is emitted **because** the
column parsed as a period. Measured:

| `col_lvl1='value'` | `col_period IS NULL` | cells |
|---|---|---|
| yes | **no** | **7,009** |
| yes | yes | 46 |
| no | no | 6,330 |
| no | yes | 11,403 |

`'value'` is a period-**success** signal 99.3% of the time. The real
period-fallback mass sits in the *other* corner: 11,403 cells in
non-period-lineage columns with no `col_period` — descriptive columns like
`Average balance ($m)`, `Interest ($m)`, and the mis-parsed `Year 2024`.

### C.2 `legal_entity` — **the finding is that it has no owner**

**It is never decided in the pipeline.** Neither the `col_dim` INSERT
(`load_v7.py:1226-1239`) nor the `cell_fact` INSERT (`:1408-1415`) names the
column. It is populated exclusively by a **one-shot migration script**:

- `mapping/migrate_add_legal_entity.py:72-74` — `ALTER TABLE … ADD COLUMN`
  on `col_dim`, `cell_fact` (and others);
- `:80-95` — derives `col_dim.legal_entity` from the column's own label, else its
  parent banner, via `legal_entity_map`;
- `:103-106` — `UPDATE cell_fact SET legal_entity = (SELECT c.legal_entity FROM col_dim c …)`.

**Fallback chain:** column label → parent banner label → NULL. There is no
document- or table-level default; `DEFAULT 'CONSOLIDATED'` exists only on
`bank_line_map` (`:78`) and `table_registry.legal_entity_default`, neither of
which is read by the data path.

**Can a later stage overwrite it? Two do, both destructively.**

1. `load_v7._delete_doc` (`:935-939`) deletes the doc's `cell_fact` and
   `col_dim`. A doc-scoped reload therefore **erases `legal_entity` for that
   document** and the loader cannot put it back. Restoring it requires re-running
   the migration by hand.
2. `build_fact_metric._write_fact` (`:464-481`) drops and recreates
   `fact_metric` from an inline DDL with no `legal_entity` column. This is
   observed, not theorised — it happened during this audit (§0.1).

**Empty = error or silent default?** Silent. `audit_coverage.value_state`
(`:94-95`) treats `legal_entity IS NULL` as equivalent to `CONSOLIDATED`, so an
unstamped Bank-only column reads as a clean group value.

### C.3 `segment_key`

**Decided in two places, and they can disagree.**

1. `load_v7.py:resolve_axis_labels` (`:553-591`) — exact normalised full-label
   match against `segment_map`, with the axis-exclusivity rule. Applied
   separately to the row axis (`:1274-1276`) and the column axis (`:1146-1147`).
2. `load_v7.py:1404-1405` — the per-cell resolution
   `row_seg or col_seg or "SEG_TOTAL"`.

**Which wins at runtime:** the row axis, then the column axis, then the default.
This matches `v_cell`/`v_cell_flat`, which read the materialised
`cell_fact.segment_key` directly — so the view and the fact agree by
construction. That part is sound.

**Fallback chain:** row label match → column label match → `SEG_TOTAL`.
All links empty → `SEG_TOTAL`, silently (gate A4). There is a third, quieter
failure at `:588-590`: when a label matches ≥2 axes as a real member and no axis
dominates, **all three axes are nulled** and a warning emitted — the cell then
takes `SEG_TOTAL`/`GLOBAL`/`IND_TOTAL`, i.e. maximum confidence from maximum
ambiguity.

**Can a later stage overwrite it?** Not in the pipeline. But
`bank_line_map.segment_key` holds a **rival** answer for the same rows
(SEG_COMMERCIAL / SEG_MARKETS, §B.2) that is never projected. Two sources of
truth, one of them disconnected.

**Empty = error or silent default?** Silent default. `fact_metric.segment_key`
is `NOT NULL` and always populated — an unstamped cell is indistinguishable from
a genuine group total, which is exactly what destroys the DBS two-book split.

### C.4 `unit`

**Decided in two places.**

1. `load_v7.py:resolve_cell_unit` (`:412-434`) — steps 1–5, per cell:
   `unit_from_value(value_raw)` → `row_unit if '%'` → `col_unit` → `row_unit` →
   `table_unit`. Called at `:1392-1393`.
2. `load_v7.py:_apply_document_default_unit` (`:1506-1552`) — step 6, doc-wide
   after every table: cells still NULL take the **modal non-NULL `table_t.unit`
   across the document**. A tie → no default, cells stay NULL.

**Which wins:** step 6 only fills what steps 1–5 left NULL, so there is no
conflict. But step 6 is where the damage is: it will happily stamp `S$m` on a
percentage row, because it is a document-level mode with no row-level evidence.
That is exactly UOB's ROE (§B.4).

**Fallback chain:** cell token → `%` row marker → column → row → table →
document mode → NULL. All empty → NULL plus one warning per table
(`:1551`, gate A7).

**Can a later stage overwrite it? Yes — `build_fact_metric` rewrites it.**
`_resolve_cell_unit` (`:184-210`) returns a promoted unit from the concept
dictionary when the concept is percent-family and the table declares no column
units, and `fact_metric.unit` records the overridden value with
`unit_source='dictionary_promoted'`. So `fact_metric.unit` can differ from
`cell_fact.unit` for the same cell (`S$m` → `%`). This is deliberate and
recorded — the only feature in this audit with a provenance flag.

**Empty = error or silent default?** Silent, at every link.

### C.5 Summary — does the silent-fallthrough shape recur?

| feature | single decision site? | silent fallthrough? | can a later stage overwrite? |
|---|---|---|---|
| `period` | yes (`load_v7.py:1373-1385`) | **yes** — 44.6% of cells, gates A1–A3 | no |
| `legal_entity` | **no owner in the pipeline** | **yes** — NULL reads as CONSOLIDATED | **yes, destructively** (reload; `fact_metric` rebuild) |
| `segment_key` | two sites, row-then-col, consistent | **yes** — `SEG_TOTAL`, gates A4/A6 | no (but `bank_line_map` holds a rival answer) |
| `unit` | two sites (per-cell, doc-modal) | **yes** — doc mode, gate A7 | **yes** (`build_fact_metric` promotion, flagged) |

Yes. The shape recurs on all four.

## Part D — concept-key provenance

### D.1 Every writer

| # | writer | target | condition | overwrites? |
|---|---|---|---|---|
| 1 | `concept/resolve_deterministic.py:112-114` | `row_dim.concept_key` | any exact alias match | **YES — unconditional.** `if cur_key == key: skip` else UPDATE (`:107-123`) |
| 2 | `concept/resolve_llm.py:169-171` | `row_dim.concept_key` | `AND concept_key IS NULL` | no — fill-only |
| 3 | `pipeline/fix_identity_misstamps.py:74-75` | `row_dim.concept_key` | keyed by `(doc,table,row)` **and** the row's current value must match an expected number | yes, deliberately |
| 4 | `pipeline/templates/stamp.py:137-140` | `row_dim.concept_key` **and `cell_fact.concept_key`** | template row alignment | **YES — unconditional.** The only writer that touches `cell_fact` |
| 5 | `concept/resolve_llm.py:188-192` | `concept_map` wildcard alias | label unambiguous corpus-wide | indirect: changes what writer 1 does on every future run |
| 6 | `mapping/backfill_map.py:162-179` | `bank_line_map.concept_key` | anchor not `human_*` | inert (§D.5) |
| 7 | `mapping/apply_dashboard_rows.py:86-98` | `bank_line_map.concept_key` | anchor exists, not `human_corrected` | inert (§D.5) |

**Which wins at runtime.** Writer 1 runs first in `concept/run.py` (`:96`) and is
unconditional, so it beats every prior manual correction. This is not a latent
hazard — it is a known, documented workaround.
`fix_identity_misstamps.py:26-31` states it plainly:

> "Because concept/run.py's deterministic pass unconditionally re-derives
> row_dim.concept_key from the CURRENT alias table on every run (it does not
> respect a prior manual correction), this script is designed to be run again,
> harmlessly, any time after concept/run.py"

So correctness depends on an **operator remembering to re-run writer 3 after
writer 1**. `run_doc.py` calls writer 1 (step 4a) and never calls writer 3.

### D.2 Lookup key at each writer

| writer | lookup key | precedence |
|---|---|---|
| 1 deterministic | `(norm(row_leaf_label_clean ?? row_leaf_label), map_table_type_norm(table_type))` | type-scoped row beats wildcard `'*'` (`resolve_deterministic.py:52-56`) |
| 2 LLM | `(norm_label, table_type)` context batch | n/a — fills NULLs only |
| 3 misstamp fixer | `(doc_id, table_id, row_id)` + expected value | n/a |
| 4 template stamp | `line_no` → template row | n/a |
| 6/7 mapping | `(bank, table_type_id, row_label_norm, parent_label_norm)` | `human_corrected > human_confirmed > ai_verified > ai_proposed` |

The gap is stark. The pipeline key has **two** fields and no parent. The map key
has **four** and the parent is what disambiguates. `map_table_type_norm` covers
129/375 tables (34%); the other 66% resolve against wildcard `'*'` aliases.

### D.3 Row-scoped or cell-scoped?

**Row-scoped, unambiguously.** `row_dim.concept_key` is one column on one row;
`resolve_deterministic._fetch_rows` (`:73-82`) selects no column information.
`cell_fact.concept_key` exists but is 0% populated (only writer 4 ever sets it,
and that path is not in the FS pipeline), and `v_cell_flat` collapses them with
`COALESCE(r.concept_key, f.concept_key)` — the row always wins.

**Therefore cell 5 (§B.5) cannot be expressed.** To express it, three things
would have to change:

1. the lookup would need the column in its key — at minimum
   `(label_norm, table_type, col_label_norm | col_unit)`;
2. `cell_fact.concept_key` would have to become the authoritative store, not a
   denormalised copy, which means inverting the `COALESCE` in `v_cell`,
   `v_cell_flat` and `v_cell_leaf`;
3. `bank_line_map` would need a column-side anchor — it currently has
   `row_label_norm` and `parent_label_norm` only, so the map cannot express it
   either.

This is a description of what is missing, not a proposal.

### D.4 `human_confirmed` anchors — where they enter, and the MERGE invariant

They enter at `mapping/apply_dashboard_rows.py` from
`mapping/dashboard_rows.yaml` (149 lines), which sets
`map_status='human_confirmed'`, `mapped_by='dashboard_rows.yaml'`,
`confidence=1.0`. Live count: **89 rows**, against 2,237 `ai_proposed`.

By bank and exhibit:

| bank | FS_INCOME_SELECTED | FS_BALANCE_SELECTED | FS_BALANCE_STATUTORY | FS_RATIOS_KEY | FS_PER_SHARE | FS_INCOME_STATUTORY | FS_HIGHLIGHTS_COMBINED |
|---|---|---|---|---|---|---|---|
| DBS | 17 | 5 | 1 | 7 | 5 | — | — |
| OCBC | 13 | — | 2 | 9 | — | 2 | — |
| UOB | — | — | 4 | — | — | — | 24 |

**MERGE invariant, verified by inspection.** MAPPING_LAYER §2.4.4 requires an
existing anchor to be left alone. Two guards:

- `backfill_map.py:56` — `PROTECTED = ("human_confirmed", "human_corrected")`;
  `:133-136` — `if existing and existing[1] in PROTECTED: continue`.
- `apply_dashboard_rows.py:79-83` — skips rows already at `human_corrected`.

**The invariant holds today, but it is enforced in application code, not in the
schema.** `backfill_map.py:167-178` is an
`INSERT … ON CONFLICT(bank, table_type_id, row_label_norm, parent_label_norm)
DO UPDATE SET concept_key=excluded.concept_key, …` — an upsert that **would**
overwrite a `human_confirmed` row. It is safe only because the Python
`continue` at `:134` runs first. There is no `WHERE map_status NOT IN (…)` on
the `DO UPDATE`, no trigger, and no CHECK. Any new writer, or any refactor that
drops the pre-check, silently overwrites human answers. I did not find a test
asserting this.

**What protects the anchors from the pipeline: nothing is needed, because the
pipeline cannot see them** (§D.5).

### D.5 Which stages can write a concept_key no human approved — and how would we tell?

**Writers 1, 2, 4 and 5 all can.** Writer 1 does so on every `run_doc` invocation
(step 4a), for every row in the corpus, from an alias table that writer 5 (the
LLM) appends to automatically. `run_doc.py` never consults `bank_line_map`,
`map_status`, or anything human-authored.

**The 89 human_confirmed rows are inert.** Grepping every reader of
`bank_line_map` across the repo:

| reader | file:line | role |
|---|---|---|
| `apply_dashboard_rows.py` | `:59, :79, :128` | writes it |
| `backfill_map.py` | `:131` | writes it |
| `audit_coverage.py` | `:115` | **reports** on it |
| `tools/timeseries_metrics.py` | `:286-288` | counts it for a report |

No reader in `pass2/`, `concept/`, `app/` or `tools/slide_kit.py`. This is
MAPPING_LAYER step 6 (the projection) — explicitly out of scope for this pass,
and confirmed **not done**. Consequence: the human sheet is documentation, not
configuration.

**How would we tell after the fact?** Partially.

- `concept_resolution_log` records `(doc, table, row, label, concept_key,
  method, confidence, ts)` for writers 1 and 2 — so a key written by
  `deterministic` or `llm` is attributable.
- **Writers 3 and 4 log nothing.** `fix_identity_misstamps.py` and
  `templates/stamp.py` update `row_dim` without a log row.
- `row_dim` itself carries no provenance column — no `stamped_by`, no
  `map_status`. Given a `row_dim.concept_key`, you cannot tell from the row
  whether a human ever saw it; you must join to `concept_resolution_log` and
  take the latest `ts`, and accept that two writers are invisible there.
- `fact_metric.resolved_by` records the *collapse* rule (`single` /
  `twin_collapse` / `prefer_table` / `conflict` / `formula`), not the origin of
  the key.

## Part E — the human sheet as a test fixture

### E.1 Does anything read it?

**The sheet is `findociq/pipeline/mapping/dashboard_rows.yaml`** (149 lines,
89 rows across 3 banks and 7 exhibit types). Two things read it:

1. **`mapping/apply_dashboard_rows.py`** — the loader. It UPSERTs the rows into
   `bank_line_map` at `human_confirmed`. Note it issues **UPDATE only**
   (`:86-98`), never INSERT, and `verify()` (`:53-70`) aborts the whole run if
   any anchor is absent from `bank_line_map` (`:118-120`). So the sheet can only
   annotate anchors that `backfill_map.py` already discovered in the corpus.

2. **`mapping/audit_coverage.py`** — the closest thing to a fixture that exists.
   It replays all 89 anchors against every (bank, quarter) and classifies each
   as `HIT` / `MISS-STRUCTURE` / `MISS-ABSENT` / `CONTAMINATED` /
   `N/A-BY-DISCLOSURE` (`:110-176`), and can emit a markdown matrix.

Nothing else. In particular, no test file imports either, and neither is called
from `run_doc.py`.

### E.2 How far is `audit_coverage.py` from being the golden fixture?

Closer than expected. It already asserts the hard part — **the structural path**:
`exact = [r for r in in_exhibit if r["label_norm"] == label and r["parent_norm"]
== parent]` (`:139-141`). That is the parent-qualified anchor the whole design
rests on, and it is already checked.

What it does **not** assert, per the brief's five dimensions:

| dimension | asserted today? | where the gap is |
|---|---|---|
| **value** | ❌ | `value_state` (`:86-107`) only checks *a* numeric cell exists. There is no expected number anywhere in the repo. |
| **period** | ⚠️ partial | `at_period = [r for r in usable if r[3] == period]` (`:100`) checks the cell's period equals the **document** period — which is exactly the value gate A1 fabricates. It cannot catch §B.3. |
| **period_span** | ❌ | not read at all. Without it FY vs 2H vs 4Q are indistinguishable (§B.4). |
| **legal entity** | ⚠️ weak | `(r[2] is None or r[2] == "CONSOLIDATED")` (`:95`) — NULL passes as CONSOLIDATED, so the §B.1 defect is invisible. |
| **segment** | ❌ | `segment_key` is selected from the anchor (`:113`) and **never used**. |
| **concept key** | ❌ | the anchor's `concept_key` is used only to look up a unit class (`:129`); it is never compared to `row_dim.concept_key`. |

### E.3 Shortest path to a golden fixture

Two things are needed, in this order:

1. **An expected-value column.** The 27 figures' correct numbers exist nowhere in
   the repo — not in `dashboard_rows.yaml` (deliberately: its header states
   "Authored by READING each exhibit's structure … never by matching a value to
   an expected figure", and that standing rule is right for *authoring*), and not
   in any CSV. The four `GT_*.csv` files at the repo root are TOC/Pillar-3 ground
   truth, not these figures. A fixture needs a **separate** file — expected
   values are an assertion target, not an authoring input, and keeping them in a
   different file preserves the standing rule.

2. **Extend `audit_coverage.value_state`** to compare `(value_num, period,
   period_span, legal_entity, segment_key)` and to join `row_dim.concept_key`,
   turning `HIT` into a real pass/fail. The traversal, the anchor resolution and
   the defect log already exist.

**Deterministic re-run is available and is the good news.** 164 `parsed.json`
audit units exist under `findociq/outputs/**/*4q25*/audit/`, and
`run_doc.py --verify-only` (`:33-34,58-59`) plus `load_doc` (`:291`) replay
load → concepts → verify from artifacts at **$0**, no Gemini call. A 4Q25 golden
test does not need to re-extract.

### E.4 What is missing today that stops the test being written

Specifically, in descending order of blocking power:

1. **No expected values.** As above. This is the only true blocker; everything
   else is a caveat about what the test would report.

2. **The test would fail by construction on `concept_key` and `segment_key`,
   for a reason unrelated to extraction.** `bank_line_map` is not projected onto
   `row_dim` (§D.5), so asserting "the concept key matches the human answer"
   compares two independently-derived values. The three DBS NII rows would fail
   on `segment_key` (SEG_TOTAL vs SEG_COMMERCIAL/SEG_MARKETS) not because
   extraction failed but because the projection does not exist. **The fixture
   should be written anyway** — that failure is the correct signal, and it is
   exactly the pass/fail the brief wants. It just needs to be labelled
   "projection not implemented", not "extraction defect".

3. **`fact_metric` cannot represent two of the assertions.** It has no
   `legal_entity` column (dropped by the rebuild, §0.1) and no `basis` column,
   while `dashboard_rows.yaml` distinguishes DBS `net_profit` (underlying,
   11,033) from `reported_net_profit` (reported, 10,933) by `basis` alone. Those
   two anchors collapse to one `fact_metric` PK. So the fixture must assert
   against **`cell_fact`**, not `fact_metric` — `cell_fact` carries
   `legal_entity` correctly and is 1:1 with the printed page.

4. **Unstable keys, mitigated.** `row_id` is positional (`load_v7.py:1287`,
   `row_id = i + 1`), so any extraction change renumbers every row below the
   change — which is why `fix_identity_misstamps.py` guards on expected values
   (`:47-57`). `table_id` embeds a period token (`:1111`). Neither is safe to
   pin a fixture on. The anchor
   `(bank, table_type_id, row_label_norm, parent_label_norm)` is the stable key,
   and `audit_coverage.py` already uses it. **This one is already solved** —
   the fixture must simply not regress to row ids.

5. **`table_type_id` covers 261/375 tables; 114 are UNCLASSIFIED.**
   `audit_coverage.load_doc_rows` filters `WHERE t.table_type_id IS NOT NULL`
   (`:73`), so anchors in unclassified exhibits report `N/A-BY-DISCLOSURE` —
   indistinguishable from "the bank didn't publish it". The fixture needs those
   two outcomes separated or it will under-report misses.

6. **`period_span` is not in the anchor.** `bank_line_map` has `period_type`
   (`instant`/`duration`) but not the printed span. As §B.4 shows, UOB 4Q25 ROE
   is FY=9.6 / 2H=7.6 and there is no 4Q at all — the fixture must state which
   span each of the 27 figures refers to, per bank, or it cannot be evaluated.

## The three seams I would fix first

Ranked by what they buy the 27-figure spine, not by code quality.

### 1. Project `bank_line_map` onto `row_dim` (G1) — MAPPING_LAYER step 6

**Why first:** it is the only finding that touches all 27 figures × 3 banks at
once, and the work it unlocks is already done. The human sheet already holds the
correct `concept_key`, `segment_key`, `legal_entity` and `basis` for the DBS
two-book split, the OCBC and UOB equivalents, and the EPS pairs. 89 rows of
verified answers are sitting one join away from the serving table and nothing
reads them. Until this lands, every other fix is measured by opinion, because
the only independent statement of the right answer is disconnected from the
thing being measured.

It also subsumes G3 and G8: a projected map is parent-qualified by construction
(the anchor is `(bank, table_type_id, row_label_norm, parent_label_norm)`), so
the three NII rows separate; and a projection is idempotent, so it stops
`resolve_deterministic` from being the last writer to run.

*Note:* this is MAPPING_LAYER step 6, which the brief lists as out of scope for
this pass. I am naming it as the top seam, not acting on it.

### 2. Make `fact_metric` stop destroying the consolidation axis (G2 + G5)

**Why second:** it is the shortest distance between a correct `cell_fact` and a
wrong dashboard. `cell_fact` already has UOB's 572,061 stamped `CONSOLIDATED`
and 485,263 stamped `BANK_SOLO` — the extraction, the column axis and the load
are all right. The number reaching serving is wrong because one grouping key
omits one field, and because the table is rebuilt from an inline DDL that
silently discards any column a migration added. That second half is not
theoretical: it happened during this audit, and it took `fact_metric` from 2,925
rows to 2,524 and deleted the column.

This is the finding with the highest ratio of blast radius to distance from
correct. It affects every Group/Bank pair in the spine — total assets, total
equity, and the balance-sheet items behind them.

### 3. Turn gate A3 into an assertion and give the fixture expected values (G4 + Part E)

**Why third:** this is the seam that converts the other two from opinion into
pass/fail. `load_v7.py:1131-1137` already computes exactly the right check — "is
the document period among this table's column periods?" — and then appends a
string to a list nobody reads. Alongside it, `:1088-1090` already detects
"period-looking column yielded no period", which is the precise signature of the
`Year 2024` defect. Both signals exist; neither has a consumer.

Pair that with the fixture: `audit_coverage.py` already resolves all 89 anchors

`legal_entity` or `basis`. The $0 replay path exists (164 4Q25 audit units,
`run_doc --verify-only`), so the test is cheap to run on every change.

failure is the point — it is seam 1's acceptance test, written before seam 1.
